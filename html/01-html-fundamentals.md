# 01. HTML Fundamentals

## What is HTML?

**What is it?**
HTML (HyperText Markup Language) is the standard markup language used to describe the *structure and content* of a web page — headings, paragraphs, links, images, forms, etc. It is not a programming language; it has no logic, loops, or variables. It just tells the browser "this is a heading," "this is a paragraph," "this is a link."

**Why was it invented / what problem does it solve?**
In 1989–1991, Tim Berners-Lee needed a way to link and share documents over the internet (the "hypertext" idea) so scientists at CERN could reference each other's papers. HTML was the simplest possible way to mark up plain text with tags so *any* browser, on any machine, could render it consistently — without needing a specific app or OS.

As the web grew, three separate concerns emerged and were deliberately split into three separate technologies:

| Concern | Technology | Question it answers |
|---|---|---|
| Structure/content | HTML | What is this thing? (a heading, a list, a form) |
| Presentation | CSS | How should it look? (color, layout, spacing) |
| Behavior | JavaScript | What should it do? (click handlers, animations, API calls) |

This separation of concerns exists because early web pages mixed styling and structure in the same tags (e.g. `<font>`, `<center>`, inline `style=""` everywhere), which made pages hard to maintain, hard to make consistent, and impossible to reuse styles across pages. Splitting them means:
- Designers can change the entire look of a site by editing one CSS file, without touching HTML.
- Content stays clean and meaningful, which helps accessibility tools and search engines understand it.
- JavaScript can be swapped or upgraded without rewriting markup.

**Real-time / real-world usage**
Every website you've ever used is built on HTML as the base layer. Frameworks like React, Angular, and Vue all still ultimately render HTML to the browser — they just generate/manage it dynamically instead of you writing static files.

**How to explain this in an interview (simple English)**
"HTML is the skeleton of a web page — it defines what content exists and what it means. CSS is the skin (how it looks), and JavaScript is the muscles (how it behaves/interacts). Keeping these separate makes websites easier to maintain, more accessible, and better for SEO, because the content structure stays clean regardless of how it's styled or scripted."

## Document Structure

**What is it?**
Every HTML document has a required skeleton:

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Page Title</title>
  </head>
  <body>
    <!-- visible content goes here -->
  </body>
</html>
```

- `<!DOCTYPE html>` — tells the browser which "mode" to render the page in.
- `<html lang="en">` — the root element; `lang` helps screen readers and translators know the language.
- `<head>` — metadata that isn't directly shown on the page (title, charset, links to CSS, SEO meta tags, favicons).
- `<body>` — everything the user actually sees/interacts with.

**Why was it invented / what problem does it solve?**
Browsers need a predictable, standard entry point to know "where does the document start, what's metadata, what's content." Without this contract, every browser vendor would render pages differently (and, historically, they did — which is exactly the problem DOCTYPE was created to fix).

### DOCTYPE and rendering modes

`<!DOCTYPE html>` is a signal to the browser: "render this using modern, standards-compliant HTML5 rules." Without it (or with an old/malformed doctype), the browser falls back into **Quirks Mode**, an old compatibility mode from the late 1990s that emulates old, buggy browser behavior (weird box-model calculations, inconsistent CSS handling).

| Mode | Trigger | Behavior |
|---|---|---|
| Standards mode | `<!DOCTYPE html>` present and correct | Modern, spec-compliant rendering |
| Quirks mode | Missing/incorrect DOCTYPE | Old Navigator 4 / IE5-style rendering bugs |
| Limited-quirks mode | Certain old DOCTYPEs | Mostly standard, minor quirks |

**Real-time / real-world usage**
You write this boilerplate once per HTML file, or it's auto-generated by your build tool / framework (Next.js, Vite, CRA). If you ever inherit a legacy page that looks "off" in weird ways (box sizing, table rendering), check if DOCTYPE is missing — that's a classic root cause.

**How to explain this in an interview (simple English)**
"DOCTYPE tells the browser to use modern rendering rules instead of falling back to old quirky behavior from the 90s. Without it, you can get inconsistent layouts across browsers."

## How Browsers Parse HTML into the DOM

**What is it?**
The DOM (Document Object Model) is an in-memory, tree-shaped representation of your HTML that JavaScript can read and manipulate. The browser doesn't "run" your HTML file directly — it *parses* it into this tree first.

**Why was it invented / what problem does it solve?**
Text (raw HTML) is not something a program can easily query or mutate. Trees are. The DOM gives JavaScript a structured API (`document.querySelector`, `.appendChild`, etc.) to read and change the page after it loads — which is the foundation of every interactive website.

### The parsing pipeline (high level)

1. **Bytes → Characters**: The browser reads raw bytes and decodes them using the detected encoding (usually UTF-8, declared via `<meta charset="UTF-8">`).
2. **Characters → Tokens**: The HTML tokenizer scans for tags, attributes, and text, producing tokens like `StartTag: div`, `Text: "hello"`, `EndTag: div`.
3. **Tokens → Nodes**: Tokens are converted into DOM node objects.
4. **Nodes → DOM Tree**: Nodes are linked into a tree based on nesting rules.

While parsing HTML, whenever the parser hits a `<link rel="stylesheet">` it triggers CSS parsing (building the **CSSOM**), and whenever it hits a `<script>` tag (without `async`/`defer`), it **blocks HTML parsing** to download and execute the script, because that script might use `document.write()` or modify the DOM in a way that changes what comes next.

This is exactly why:
- CSS is placed in `<head>` — so styles are known before content is painted (avoids flash of unstyled content).
- Scripts are placed at the bottom of `<body>`, or given `defer`/`async`, so they don't block the initial HTML parse.

```html
<script src="app.js" defer></script>
<!-- defer: downloads in parallel, executes after HTML parsing completes, in order -->

<script src="analytics.js" async></script>
<!-- async: downloads in parallel, executes as soon as ready (order not guaranteed), can interrupt parsing -->
```

5. The parser is also **error-tolerant**: unlike XML, HTML parsing doesn't throw a hard error on malformed markup (e.g., unclosed `<p>` tags). The spec (HTML5) defines exact recovery rules so all browsers handle broken HTML the same way.

**Real-time / real-world usage**
Understanding this pipeline is exactly what separates "I write HTML" from "I understand why my page has a flash of unstyled content" or "why does my script fail because an element doesn't exist yet" (script ran before DOM finished parsing that element — classic bug fixed by `defer` or moving script to the end of body, or wrapping in `DOMContentLoaded`).

**How to explain this in an interview (simple English)**
"The browser reads HTML top to bottom, converts it into a tree of objects called the DOM, and JavaScript can then read/modify that tree. Scripts without `defer`/`async` block this parsing, which is why we either put `<script>` at the end of `<body>` or use `defer`, so the page renders faster and JS doesn't try to touch elements that don't exist yet."

## Block vs Inline Elements

**What is it?**
Every HTML element has a default "display" behavior:

| | Block | Inline |
|---|---|---|
| Takes full width available | Yes | No — only as wide as its content |
| Starts on a new line | Yes | No — flows with surrounding text |
| Can contain other block/inline elements | Yes | Generally only other inline elements |
| Examples | `<div>`, `<p>`, `<h1>`–`<h6>`, `<ul>`, `<section>`, `<form>` | `<span>`, `<a>`, `<strong>`, `<em>`, `<img>`, `<label>` |
| Can set width/height directly | Yes | No (unless `display` is changed) |

**Why was it invented / what problem does it solve?**
Text documents naturally have two kinds of content: things that form their own line (paragraphs, headings) and things that sit inside a line of text (bold words, links). The block/inline distinction models that natural document flow before any CSS is even applied.

Note: this is the *default* behavior defined by the browser's built-in stylesheet — you can override it with CSS `display: inline`, `display: block`, `display: inline-block`, `display: flex`, etc. So "block vs inline" is really about defaults, not a permanent rule.

**Real-time / real-world usage**
- Building a nav bar: `<ul>` (block) containing `<li>` (block) containing `<a>` (inline) — commonly the `<a>` is switched to `display: block` or `inline-block` so the entire clickable area is easier to hit (bigger touch target).
- A common interview trap: putting a block element (like a `<div>`) inside an inline element (like `<a>` in old HTML4) was invalid; HTML5 relaxed this and `<a>` can now wrap block-level content.

**How to explain this in an interview (simple English)**
"Block elements stack vertically and take the full width, like paragraphs. Inline elements sit inside a line of text and only take as much width as their content, like a bold word. It's just the browser's default layout behavior — CSS `display` can always override it."

## Void Elements

**What is it?**
Void elements are elements that cannot have any children/content and don't need (or use) a closing tag, because there's nothing to "close" — they represent a single, self-contained thing.

```html
<img src="cat.jpg" alt="A cat" />
<br />
<hr />
<input type="text" />
<meta charset="UTF-8" />
<link rel="stylesheet" href="style.css" />
<source src="video.mp4" type="video/mp4" />
```

Full list (commonly asked): `area`, `base`, `br`, `col`, `embed`, `hr`, `img`, `input`, `link`, `meta`, `param`, `source`, `track`, `wbr`.

**Why was it invented / what problem does it solve?**
Some elements simply have no concept of "inner content" — an `<img>` doesn't wrap text, it just points to a resource via an attribute. Requiring `</img>` would add noise with zero benefit. The self-closing slash (`<br />`) is optional in HTML5 (it's an XHTML-compatibility habit) — `<br>` alone is perfectly valid HTML5.

**Real-time / real-world usage**
This matters in interviews mostly as a "gotcha" — knowing that `<img>`, `<input>`, `<br>` don't need (and technically shouldn't have) closing tags shows you understand the HTML spec, not just "how things look in practice." In JSX (React), *all* elements including void ones must be self-closed (`<img />`, `<input />`) because JSX requires well-formed XML-like syntax — a common source of confusion for people used to plain HTML.

**How to explain this in an interview (simple English)**
"Void elements are tags that can't have children, like `<img>`, `<br>`, `<input>` — so they don't need a closing tag. In JSX though, you must self-close them because JSX is stricter than HTML."

## Character Encoding and HTML Entities

**What is it?**
Character encoding is the rulebook the browser uses to turn raw *bytes* into actual *characters* on screen. `<meta charset="UTF-8">` in `<head>` tells the browser which rulebook to use. HTML entities are a separate but related mechanism: special text sequences like `&amp;`, `&lt;`, `&copy;` that represent characters you can't (or shouldn't) type directly into HTML source, either because the character has special meaning to the parser (`<`, `>`, `&`) or because it's not easy to type on a keyboard (`©`, `é`, non-breaking space).

```html
<head>
  <meta charset="UTF-8" />
</head>
<body>
  <!-- Without entities, this line would look like broken/invalid markup to the parser -->
  <p>To write a less-than sign, use &lt;, not &lt;the raw character&gt;.</p>
  <p>Terms &amp; Conditions</p>
  <p>Copyright &copy; 2026 &mdash; All rights reserved.</p>
  <p>Non-breaking space example: 10&nbsp;km (keeps "10" and "km" on the same line)</p>
</body>
```

| Entity | Renders as | Why you need it |
|---|---|---|
| `&lt;` | `<` | A raw `<` would be parsed as the start of a tag |
| `&gt;` | `>` | Keeps closing-bracket-looking text from confusing the parser |
| `&amp;` | `&` | A raw `&` would start being interpreted as the beginning of another entity |
| `&quot;` | `"` | Needed inside attribute values that are themselves quoted with `"` |
| `&nbsp;` | (non-breaking space) | Prevents the browser from line-breaking between two words/numbers |
| `&copy;`, `&mdash;`, `&#233;` (or `&eacute;`) | `©`, `—`, `é` | Symbols/accented characters not always convenient to type directly |

**Why was it invented / what problem does it solve?**
Before UTF-8 became the near-universal default (it wasn't always — older pages used encodings like ISO-8859-1 or Windows-1252), a page's bytes could be decoded using the *wrong* rulebook, producing "mojibake" — garbled text like `Ã©` instead of `é`. Declaring `<meta charset="UTF-8">` (and actually saving/serving the file as UTF-8 bytes) removes that ambiguity entirely, since UTF-8 can represent virtually every character in every language. HTML entities solve a *different*, older problem: `<` and `&` are reserved by the HTML parser itself (they start tags and entities respectively), so you need an escape mechanism to display them literally as text instead of having the parser try to interpret them as markup.

**Real-time / real-world usage**
- A page that shows garbled characters (`Ã©` instead of `é`, or a "�" replacement character) is almost always a missing/incorrect `charset` declaration, or a mismatch between the declared charset and the actual bytes the server sent — a real, recurring production bug, especially with legacy CMS content or copy-pasted text from Word/Google Docs.
- Rendering any user-typed text that might contain `<`, `>`, or `&` as literal text (not by concatenating it into an HTML string) relies on the browser/templating engine auto-escaping these into entities — this is also *why* `textContent` (see file 09) is XSS-safe: it handles this escaping for you automatically, whereas hand-built HTML strings must escape it manually or risk both broken rendering and injection bugs.
- `&nbsp;` is commonly used to glue a number to its unit ("10&nbsp;km", "$5&nbsp;.00") so they never wrap onto separate lines.

**How to explain this in an interview (simple English)**
"`<meta charset='UTF-8'>` tells the browser which rulebook to use to turn bytes into characters — get it wrong and you see garbled text (mojibake). HTML entities like `&lt;`, `&amp;`, `&copy;` are how you display characters that either have special meaning to the HTML parser (`<`, `&`) or aren't easy to type directly. This is also why safely rendering user input as `textContent` instead of raw HTML matters — the browser auto-escapes special characters for you instead of letting them be interpreted as markup."

## Quick Summary Table

| Concept | One-liner |
|---|---|
| HTML | Markup language describing structure/content of a page |
| CSS/JS separation | Keeps style and behavior independent of content for maintainability |
| DOCTYPE | Forces standards-mode rendering, avoids quirks mode |
| DOM | Tree representation of HTML that JS can query/mutate |
| Parsing | Bytes → tokens → nodes → DOM tree; blocking scripts pause this |
| Block elements | Full width, new line, stack vertically by default |
| Inline elements | Flow with text, only as wide as content |
| Void elements | Self-contained tags with no children/closing tag (`img`, `br`, `input`) |
| Character encoding | `<meta charset="UTF-8">` tells the browser how to decode bytes into characters; wrong/missing charset causes mojibake |
| HTML entities | Escape sequences (`&lt;`, `&amp;`, `&copy;`, `&nbsp;`) for characters reserved by the parser or hard to type |
