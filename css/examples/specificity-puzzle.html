Specificity Puzzles

Each box below has two conflicting rules. Inspect the element in DevTools to confirm which rule actually applies, then read the explanation.

Puzzle 1: Class vs Element

.highlight { color: blue; }
p { color: red; }

This text should be BLUE.

A class (0,0,1,0) always beats a plain element selector (0,0,0,1), no matter the source order.

Puzzle 2: ID vs Three Stacked Classes

.a.b.c { color: red; }
#winner { color: green; }

This text should be GREEN.

A single ID (0,1,0,0) beats any number of stacked classes (here, 0,0,3,0) -- compare the ID column first.

Puzzle 3: Source-Order Tie-Break

.tag { color: red; }   /* first */
.tag { color: purple; } /* second, same specificity */

This text should be PURPLE.

Identical specificity (0,0,1,0) on both rules -- the one written LATER in the CSS wins.

Puzzle 4: :not() Adds Its Argument's Specificity

li { color: red; }
li:not(.skip) { color: teal; }
  • This item should be TEAL (not .skip)
  • This item is red because it HAS .skip, so :not(.skip) doesn't match it -- falls back to the plain "li" rule
:not(.skip) has the specificity of its argument, so li:not(.skip) = element + class = (0,0,1,1), beating plain li = (0,0,0,1).

Puzzle 5: !important Beats Higher Specificity

#strong-id { color: red; }
.weak-but-important { color: orange !important; }

This text should be ORANGE.

Normally an ID (0,1,0,0) crushes a class (0,0,1,0). But !important jumps the class rule into a higher priority tier that beats ANY normal (non-important) rule, regardless of specificity.

Puzzle 6: :where() Has Zero Specificity

:where(.card, .panel) h2 { color: red; }
.override-me { color: green; }

This heading should be GREEN.

:where(...) always contributes zero specificity, so :where(.card, .panel) h2 is only as specific as "h2" alone (0,0,0,1) -- a single class (0,0,1,0) on the element itself easily overrides it. This is exactly why :where() is popular for writing easily-overridable base/reset styles.
